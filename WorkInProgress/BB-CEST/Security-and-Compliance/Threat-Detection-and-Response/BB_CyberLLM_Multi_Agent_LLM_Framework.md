## Description

CyberLLM is a multi-agent, LLM-orchestrated cybersecurity framework designed to support autonomous vulnerability detection and guarded remediation in Software Defined Vehicles (SDVs). The framework combines deterministic security analysis with LLM-based reasoning to identify vulnerabilities across heterogeneous automotive engineering artifacts while ensuring that security-relevant actions are validated before execution.

The detection workflow analyzes three main categories of engineering artifacts: source code, runtime and communication logs, and ECU/service deployment topologies. An always-active deterministic analysis layer applies regular-expression rules, Abstract Syntax Tree (AST)-based analyzers, log-analysis rules, and deployment-topology graph checks. Static-analysis tools such as Bandit and Semgrep can additionally be integrated where applicable.

The deterministic findings provide reproducible grounding information for an LLM-based refinement stage. LLM agents analyze these findings and can identify additional semantic vulnerabilities that are difficult to detect through static patterns alone, including data races, time-of-check/time-of-use (TOCTOU) problems, use-after-free vulnerabilities, and integer overflow.

Findings produced by the different detection mechanisms are normalized into a common representation containing information such as rule identifier, severity, evidence, explanation, source agent, affected asset category, and source-code location. A dedicated Decision Agent aggregates the detected vulnerabilities and selects an appropriate response tier:

none → soft → moderate → hard

The decision can additionally incorporate verified cross-session memory containing information about previous security incidents and successful remediation strategies. Historical information follows an escalate-only principle: previous experience can increase the response level but cannot reduce the response selected for the current incident.

An Action Generator converts the selected response into a multi-step remediation plan using deterministic security playbooks and, where enabled, an MCP-style tool registry. Before execution, each proposed action is evaluated by a Security Guard against contextual security properties including task alignment, action alignment, source authorization, and data isolation. An independent LLM-based action-alignment oracle provides an additional validation layer but cannot override deterministic security restrictions.

CyberLLM also provides a symmetric attack pipeline for generating controlled and non-destructive attack scenarios. This enables attack and defense mechanisms to be evaluated against equivalent vulnerabilities and automotive cybersecurity scenarios.

## Rationale

Software Defined Vehicles increasingly rely on complex software stacks, networked ECUs, external services, over-the-air updates, vehicle communication networks, and AI-enabled components. Consequently, cybersecurity vulnerabilities can originate at several layers, including application source code, runtime behavior, communication logs, and ECU/service deployment topology.

Traditional cybersecurity tools typically analyze these layers independently. Deterministic static and rule-based analyzers provide reproducible detection of known vulnerability patterns but may fail to identify semantic or context-dependent vulnerabilities. LLMs can provide stronger contextual reasoning and identify complex vulnerability patterns, but their probabilistic behavior introduces risks such as hallucinated findings, incorrect interpretations, and unsafe remediation proposals.

CyberLLM therefore combines deterministic security analysis with LLM-based reasoning rather than relying exclusively on either approach. Deterministic mechanisms establish a reproducible security-analysis baseline, while LLM agents refine the results and identify vulnerabilities requiring deeper semantic interpretation.

At the response level, deterministic runtime guards constrain actions generated by probabilistic agents. This hybrid architecture aims to increase cybersecurity automation while retaining explicit control, auditability, and validation of actions affecting safety- and security-critical vehicle systems.

## What is needed to Design and Implement

Automotive source code, runtime and communication logs, ECU/service deployment descriptions, cybersecurity rules, vulnerability definitions, topology constraints, security policies, LLM models, prompting strategies, deterministic security analyzers, provenance mechanisms, response playbooks, remediation tools, persistent incident storage, and validation mechanisms.

A common representation for detected security findings is required so that results from deterministic and AI-based scanners can be aggregated and processed by downstream decision agents.

The deterministic detection layer requires machine-readable security rules covering source-code analysis, runtime/log analysis, and deployment-topology invariants.

The response subsystem requires explicit security objectives and mappings between authorized actions and those objectives. Actions should provide clearly defined schemas, side effects, preconditions, postconditions, and rollback behavior.

Cross-session learning additionally requires tamper-evident storage mechanisms so that historical security information can influence future decisions without allowing unverified memory entries to modify security behavior.

## What is needed to build and run

Python environment, required cybersecurity and AI libraries, access to suitable LLM models through configured inference interfaces, deterministic security rules, static-analysis tools such as Bandit and Semgrep where applicable, and representative automotive engineering artifacts.

Depending on the analysis scenario, input data can include automotive source-code repositories, runtime and telemetry logs, CAN or other communication logs, and ECU/service/actor/datasource topology descriptions.

The response functionality additionally requires a security-rule knowledge base, persistent storage for signed security incidents and remediation history, cryptographic verification mechanisms, security playbooks, authorized remediation tools, and sandboxed execution and rollback mechanisms.

Both locally deployed and externally hosted LLMs can be integrated depending on privacy, cybersecurity, latency, and computational requirements.

## Non-Functional Requirements

Deterministic enforcement of security-critical constraints, traceability of vulnerability findings, provenance of analyzed information, auditability of autonomous decisions, reproducibility of deterministic analyses, tamper-resistant memory, protection against memory poisoning, controlled execution of remediation actions, rollback capability, isolation of security tools, and validation of AI-generated actions before execution.

The framework should additionally provide high detection precision, extensibility of security rules, support for heterogeneous programming languages, interoperability with automotive software and communication artifacts, and fail-safe behavior when AI-generated outputs are malformed, uncertain, or violate predefined security policies.

## Potential obstacles

LLM hallucinations, false or incomplete vulnerability findings, missed semantic vulnerabilities, prompt injection, memory poisoning, unsafe remediation proposals, incorrect interpretation of automotive software behavior, incomplete security rules, inaccurate deployment-topology descriptions, and dependency on the quality of security context supplied to the agents.

Autonomous cybersecurity actions introduce additional risks in safety-critical automotive systems. Probabilistic agent decisions therefore cannot directly authorize security-sensitive modifications and require deterministic validation before execution.

Scalability can also become challenging when analyzing large software repositories, extensive vehicle logs, complex ECU/service topologies, or multiple interacting security incidents. The quality of LLM-based analysis depends on the selected model and available contextual information, while deterministic analyzers remain limited by their predefined rules.

CyberLLM addresses these risks through deterministic guards, independent action validation, authenticated provenance, tamper-evident memory, constrained tool execution, and rollback mechanisms.

## System Context

CyberLLM operates as part of an SDV cybersecurity and AI-assisted engineering toolchain.

Automotive source code, runtime logs, communication information, and deployment-topology descriptions are provided to dedicated security-analysis agents. Deterministic scanners first identify known vulnerabilities and policy violations using regex rules, AST analyzers, log-analysis rules, and topology constraints.

The deterministic findings provide grounding information to LLM-based scanners, which refine the results and search for additional semantic vulnerabilities. Findings produced by the different mechanisms are normalized and merged before being forwarded to the Decision Agent.

The Decision Agent evaluates the detected vulnerabilities, affected assets, severity, confidence, previous incidents, and remediation outcomes to select an appropriate response tier.

The Action Generator transforms the selected response into an executable remediation plan based on deterministic security playbooks and, where enabled, tools obtained from an MCP-style registry.

Before execution, each proposed action passes through the Security Guard. The guard verifies task alignment, action alignment, source authorization, and data isolation. An independent action-alignment oracle provides an additional validation layer. Refused actions trigger re-planning instead of execution.

Approved actions can be executed with precondition and postcondition checking and rollback support. Successful outcomes can be stored in signed cross-session memory and subsequently used to inform future security decisions.

A parallel attack workflow performs passive reconnaissance and generates controlled, non-destructive attack scenarios. An Ethics Guard verifies authorization, scope, and destructive behavior before generated attack artifacts are accepted.

A simplified system flow is:

Automotive Engineering Artifacts
→ Deterministic Security Analysis
→ LLM Security Refinement
→ Finding Normalization and Aggregation
→ Decision Agent
→ Action Generator
→ Security Guard
→ Controlled Execution / Re-planning
→ Signed Incident Memory

In parallel:

Detected Vulnerabilities
→ Attack Orchestrator
→ Attack Generator
→ Ethics Guard
→ Controlled Attack Scenario
